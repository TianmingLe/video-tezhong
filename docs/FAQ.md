# 常见问题解答（FAQ）

本文档涵盖 Desktop 应用与 MediaCrawler 核心模块的常见问题排查指南。每个问题均包含**现象描述**、**根因分析**、**分步解决方案**与**预防建议**。

---

## Desktop 常见问题

### Q: 应用启动白屏/黑屏怎么办？

**现象描述**
- 双击应用图标后窗口打开，但内容区域完全空白或黑色，没有任何 UI 元素加载出来。
- 有时标题栏正常显示，但主内容区无法渲染。

**根因分析**
- Electron 渲染进程崩溃或 preload 脚本加载失败。
- 显卡驱动兼容性问题导致 GPU 进程无法启动。
- 用户数据目录损坏或权限不足，导致主进程无法读取必要配置。
- 杀毒软件/防火墙拦截了 Electron 内部资源加载。

**分步解决方案**
1. 强制刷新：按 `Ctrl+R`（Windows/Linux）或 `Cmd+R`（macOS）尝试重新加载渲染进程。
2. 以安全模式启动：在终端中运行应用并附加 `--disable-gpu` 参数，排除显卡驱动问题。
3. 清除 GPU 缓存：删除用户数据目录下的 `GPUCache` 文件夹，路径通常为：
   - Windows: `%APPDATA%/OmniScraper Desktop/GPUCache`
   - macOS: `~/Library/Application Support/OmniScraper Desktop/GPUCache`
   - Linux: `~/.config/OmniScraper Desktop/GPUCache`
4. 重置用户数据：备份并删除整个用户数据目录，让应用重新初始化。
5. 检查杀毒软件日志，将应用添加到白名单后重启。

**预防建议**
- 保持操作系统和显卡驱动为最新稳定版本。
- 避免使用第三方"系统优化"工具清理应用数据目录。
- 在企业环境中提前将应用加入终端安全软件白名单。

### Q: Python 检测失败怎么办？

**现象描述**
- 首次启动或执行任务时弹出提示"未检测到 Python"或"Python 版本不符合要求"。
- 设置页中 Python 环境状态显示为红色错误。

**根因分析**
- 系统中未安装 Python，或安装的版本低于 3.11。
- Python 已安装但不在系统 `PATH` 环境变量中。
- 使用了不兼容的 Python 发行版（如某些精简版未包含标准库）。
- 多版本共存时，`python` 与 `python3` 命令指向了错误版本。

**分步解决方案**
1. 打开终端，执行 `python3 --version` 或 `python --version`，确认是否已安装及版本号。
2. 若未安装或版本低于 3.11，前往 [python.org](https://www.python.org/downloads/) 下载并安装 3.11+。
3. 安装时务必勾选 **"Add Python to PATH"**（Windows）或确保 `/usr/local/bin` 在 PATH 中（macOS/Linux）。
4. 若多版本共存，在应用设置中指定正确的 Python 可执行文件绝对路径。
5. 重新启动 Desktop 应用，使环境变量变更生效。

**预防建议**
- 推荐使用官方 CPython 发行版，避免使用系统自带的旧版本 Python。
- 使用 `pyenv` 或 `uv` 管理 Python 版本，确保项目隔离。
- 在团队部署文档中明确 Python 版本要求。

### Q: 任务运行失败但看不到错误信息？

**现象描述**
- 任务状态显示为"失败"，但日志面板中只有少量输出，看不到明确的报错堆栈。
- 或者日志在关键位置被截断，无法定位问题。

**根因分析**
- 日志缓冲区容量有限，高频输出导致早期错误信息被滚动覆盖。
- Python 子进程异常退出时标准错误流未完全捕获。
- 任务超时后被强制终止，来不及输出完整错误。
- 日志级别过滤设置过高，DEBUG/ERROR 级别日志未显示。

**分步解决方案**
1. 打开任务详情页，点击"导出日志"按钮，将完整日志保存到本地文件后查看。
2. 在设置中调高日志保留行数限制，或清理旧日志释放存储空间。
3. 检查任务是否因超时失败，适当延长超时时间后重试。
4. 手动在终端中运行相同的 Python 命令，观察实时输出：
   ```bash
   cd MediaCrawler
   python main.py <对应参数>
   ```
5. 若日志文件本身损坏，前往用户数据目录的 `logs` 文件夹查找原始 `.log` 文件。

**预防建议**
- 对关键任务适当延长超时时间，避免复杂操作被中断。
- 定期导出并归档重要任务的日志，不要仅依赖应用内缓冲区。
- 在脚本中显式添加 `try/except` 与日志记录，确保异常信息落盘。

### Q: 如何导出日志进行反馈？

**现象描述**
- 需要向开发者反馈问题，但不知道应该提供哪些日志文件。
- 不清楚如何打包日志以避免泄露敏感信息。

**根因分析**
- 应用日志分散在多个目录（运行日志、崩溃报告、主进程日志）。
- 用户担心日志中包含 Cookie、API Key 等隐私数据。

**分步解决方案**
1. 在 Desktop 应用中进入"设置"页面，点击"反馈问题"按钮。
2. 填写问题描述后点击"生成并复制"，系统会自动收集：
   - 应用版本、操作系统、架构信息
   - 最近任务的状态与摘要
   - 相关运行日志（自动脱敏处理）
3. 若需手动导出，前往用户数据目录：
   - Windows: `%APPDATA%/OmniScraper Desktop/logs`
   - macOS: `~/Library/Application Support/OmniScraper Desktop/logs`
   - Linux: `~/.config/OmniScraper Desktop/logs`
4. 复制对应 `runId` 的 `.log` 文件，检查并手动删除其中可能包含的 Cookie、Token 字段。
5. 将脱敏后的日志粘贴到 GitHub Issue 或发送给技术支持。

**预防建议**
- 在提交日志前使用文本编辑器的查找替换功能，批量删除敏感字段。
- 开启应用的"自动脱敏"选项（如有），减少手动处理工作量。
- 避免在公共论坛直接粘贴完整日志，优先使用私信或加密渠道。

### Q: 更新检查失败怎么办？

**现象描述**
- 点击"检查更新"后长时间无响应，随后提示"检查更新失败"。
- 或提示发现新版本但下载进度始终为 0%。

**根因分析**
- 网络连接不稳定，无法访问 GitHub Releases API。
- 所在地区对 GitHub/CDN 访问受限，导致下载超时。
- 企业网络中的代理或防火墙阻止了自动更新请求。
- 本地缓存的更新元数据损坏。

**分步解决方案**
1. 确认设备可正常访问 `github.com`，尝试在浏览器中打开项目 Releases 页面。
2. 若网络受限，配置系统代理或应用内代理后重试。
3. 临时关闭代理再试一次，排除代理配置错误导致的 SSL 握手失败。
4. 手动前往 GitHub Releases 页面下载最新版本的安装包进行覆盖安装。
5. 删除用户数据目录下的 `update-cache` 文件夹，清除可能损坏的缓存后重启应用。

**预防建议**
- 在企业内网环境中提前配置好可靠的 HTTP 代理。
- 关注项目官方渠道（如微信群、GitHub Discussions），在自动更新不可用时及时获取手动安装包。
- 定期备份用户数据，避免覆盖安装导致配置丢失。

### Q: 数据库被锁定/只读模式？

**现象描述**
- 应用启动时弹出警告"数据库已以只读模式打开"。
- 无法保存模板、无法记录任务历史，或提示"database is locked"。

**根因分析**
- SQLite 数据库文件被另一个进程占用（如同时打开了两个应用实例）。
- 数据库文件权限被设置为只读。
- 数据库文件位于网络驱动器或同步盘（如 OneDrive/iCloud）中，被云同步服务锁定。
- 上一次应用异常退出导致 SQLite 留下了 `-journal` 或 `-wal` 临时文件。

**分步解决方案**
1. 打开系统任务管理器/活动监视器，确认没有重复的 Desktop 进程在运行，结束多余的进程后重启应用。
2. 检查数据库文件权限：
   - 找到用户数据目录下的 `db.sqlite3`（或 `db` 文件夹中的 `.sqlite3` 文件）。
   - 右键/属性中确保当前用户具有读写权限。
3. 若数据库位于云同步目录，将用户数据目录迁移到本地非同步路径，或在应用设置中修改数据目录。
4. 关闭应用后，手动删除与数据库同目录下的 `.sqlite3-journal`、`.sqlite3-wal`、`.sqlite3-shm` 临时文件，然后重新启动。
5. 若上述方法无效，备份并删除数据库文件，应用会重新创建空数据库（注意：这将清空任务历史和模板配置）。

**预防建议**
- 避免同时运行多个应用实例。
- 不要将用户数据目录放置在云同步文件夹内。
- 定期备份数据库文件，防止损坏后无法恢复历史数据。

### Q: 如何清理旧日志释放空间？

**现象描述**
- 磁盘空间不足，发现用户数据目录占用大量空间。
- 日志文件数量过多，查找特定任务日志困难。

**根因分析**
- 每次运行任务都会生成独立的日志文件，长期累积未清理。
- 高频率调试运行产生了大量短日志。
- 未设置自动清理策略。

**分步解决方案**
1. 打开 Desktop 应用，进入"设置"页面。
2. 点击"清理旧日志"按钮，系统会扫描并显示可删除的旧日志数量。
3. 确认后，应用将保留最近的 50 个日志文件，删除更早的日志。
4. 若需手动清理，前往用户数据目录的 `logs` 文件夹，按修改日期排序后删除旧的 `.log` 文件。
5. 检查 `results/runs/` 目录下是否有过期的运行产物（如临时视频、截图），按需删除。

**预防建议**
- 每月定期执行一次日志清理。
- 对长期运行的自动化部署，设置定时任务清理超过 30 天的日志。
- 在日志量大的场景中，将日志保留数从 50 调整为更小的值。

## MediaCrawler 常见问题

### Q: 登录失败/Cookie 过期？

**现象描述**
- 启动爬虫时提示"登录失败"、"Cookie 已过期"或"需要扫码登录"。
- 之前能正常运行的任务突然无法获取数据。

**根因分析**
- 平台（抖音、小红书、B站等）的登录态有效期到期，需要重新授权。
- Cookie 文件被意外删除或损坏。
- 账号在别处登录导致当前会话被踢出。
- 平台风控策略升级，要求二次验证或验证码。

**分步解决方案**
1. 删除旧的 Cookie 缓存文件，通常位于项目目录的 `cookies/` 或 `browser_data/` 文件夹中。
2. 使用 CDP（Chrome DevTools Protocol）模式重新登录：
   ```bash
   python main.py --platform xhs --lt qrcode
   ```
3. 根据终端提示完成扫码或短信验证，等待浏览器自动保存新的 Cookie。
4. 若使用账号密码登录失败，尝试切换为二维码登录方式，绕过验证码拦截。
5. 检查账号是否被平台限制登录，必要时更换账号或降低请求频率。

**预防建议**
- 定期（如每周）手动刷新一次登录态，避免在批量任务中途过期。
- 使用专用的爬虫账号，避免与日常使用账号冲突导致被踢下线。
- 开启自动保存 Cookie 功能，确保每次成功登录后都会持久化到本地。

### Q: 视频下载失败？

**现象描述**
- 任务日志中显示"视频下载失败"、"HTTP 403"或"连接超时"。
- 下载的文件大小为 0 KB 或不完整。

**根因分析**
- 视频 URL 包含时效性签名，在获取到 URL 后未及时下载导致链接过期。
- 平台对下载请求进行了 Referer 或 User-Agent 校验。
- 本地磁盘空间不足，无法写入完整文件。
- 网络不稳定或代理 IP 被平台封禁。

**分步解决方案**
1. 检查磁盘空间，确保目标下载目录有充足剩余空间。
2. 在配置中增加下载重试次数和超时时间：
   ```yaml
   download:
     max_retries: 5
     timeout: 60
   ```
3. 确认请求头中包含了正确的 `Referer`（如 `https://www.douyin.com/`）。
4. 若使用代理，尝试更换代理 IP 后重试。
5. 对于大文件，启用分片下载或流式写入，避免内存溢出导致写入失败。

**预防建议**
- 获取视频 URL 后立即发起下载，减少链接过期概率。
- 使用稳定的住宅代理 IP，降低被封禁风险。
- 监控磁盘空间，设置告警阈值（如剩余空间 < 5GB 时暂停任务）。

### Q: ASR 转写失败？

**现象描述**
- 视频下载成功，但在语音转文字阶段报错"ASR 失败"或"转写结果为空"。
- 日志中显示 FFmpeg 提取音频失败或 ASR API 返回错误。

**根因分析**
- 视频本身没有音轨，或音轨格式不受 FFmpeg 支持。
- FFmpeg 未正确安装或版本过旧。
- ASR 服务（如 Whisper API）的 API Key 无效或余额不足。
- 音频文件过大，超出了 ASR 服务的单次处理时长限制。

**分步解决方案**
1. 确认 FFmpeg 已安装且版本 >= 5.0：
   ```bash
   ffmpeg -version
   ```
2. 手动用 FFmpeg 提取视频音频，验证源文件是否有音轨：
   ```bash
   ffmpeg -i input.mp4 -vn -acodec copy output.aac
   ```
3. 检查 ASR 配置中的 API Key 和 Base URL 是否正确，余额是否充足。
4. 若音频过长，在配置中启用音频分段处理：
   ```yaml
   asr:
     segment_length: 300
   ```
5. 尝试将音频转换为 ASR 服务推荐的格式（如 16kHz 单声道 WAV）后重试。

**预防建议**
- 在批量任务前抽样检查视频是否包含音轨。
- 使用本地 Whisper 模型替代在线 API，避免网络波动和额度限制。
- 保持 FFmpeg 为较新版本，确保对现代编码格式的兼容性。

### Q: OCR 不可用？

**现象描述**
- 任务配置中启用了 OCR，但运行时报错"OCR 服务未初始化"或"识别结果为空"。
- 截图中的文字未被提取。

**根因分析**
- OCR 依赖的库（如 PaddleOCR、Tesseract）未安装或模型文件缺失。
- GPU 环境配置错误，导致 OCR 后端无法加载 CUDA 驱动。
- 输入图片分辨率过低或文字模糊，超出 OCR 识别能力。
- 在 Docker/容器环境中缺少必要的系统依赖库。

**分步解决方案**
1. 确认已安装 OCR 依赖：
   ```bash
   pip install paddleocr
   ```
2. 首次运行时会自动下载模型文件，确保网络畅通且磁盘空间充足。
3. 若使用 GPU 版本报错，临时切换到 CPU 模式排查：
   ```yaml
   ocr:
     use_gpu: false
   ```
4. 检查输入图片质量，确保文字清晰、对比度足够。
5. 在 Linux 容器中运行时，安装额外的系统库：
   ```bash
   apt-get install -y libgl1-mesa-glx libglib2.0-0
   ```

**预防建议**
- 在 requirements 中固定 OCR 相关库的版本，避免自动升级导致不兼容。
- 对低质量视频源，先进行图像增强（对比度、锐化）再送入 OCR。
- 在部署文档中明确 OCR 的系统级依赖清单。

### Q: 批处理中断如何恢复？

**现象描述**
- 批量处理大量视频时，任务因网络波动、程序崩溃或手动取消而中断。
- 重新启动后不希望从头开始，而是继续未完成的任务。

**根因分析**
- 默认情况下每次运行都会重新处理整个列表，没有记录已处理项的状态。
- 中断时正在进行的子任务数据可能未完全落盘。

**分步解决方案**
1. 确认任务配置中启用了断点续传/处理注册表功能：
   ```yaml
   batch:
     enable_registry: true
     registry_path: "data/processed_registry.json"
   ```
2. 中断后重新运行相同的命令，程序会自动跳过已处理过的视频 ID。
3. 若需要强制重新处理某条数据，手动从 `processed_registry.json` 中删除对应条目后重启。
4. 检查输出目录中已生成的文件，确认中断前的进度。
5. 对于数据库模式存储的任务，使用 `status` 字段筛选出 `pending` 的记录继续处理。

**预防建议**
- 始终开启处理注册表功能进行大批量任务。
- 将批处理拆分为多个小批次，降低单次中断的影响范围。
- 定期备份 `processed_registry.json`，防止文件损坏导致重复处理。

### Q: 代理 IP 被封怎么办？

**现象描述**
- 请求频繁返回 403 Forbidden、验证码页面或"操作频繁"提示。
- 同一 IP 下所有账号均无法正常获取数据。

**根因分析**
- 请求频率过高，触发了平台的风控阈值。
- 使用的代理 IP 质量差，已被平台标记为数据中心 IP。
- 代理池配置错误，实际未生效或所有 IP 已耗尽。

**分步解决方案**
1. 降低并发数和请求频率：
   ```yaml
   proxy:
     max_concurrency: 2
   crawler:
     sleep_interval: 3
   ```
2. 更换为高质量的住宅代理或移动代理服务。
3. 检查代理池配置，确保代理可用性检测正常：
   ```bash
   python -m proxy.proxy_ip_pool --test
   ```
4. 启用请求间隔随机化，避免固定频率触发风控：
   ```yaml
   crawler:
     sleep_interval: [2, 5]
   ```
5. 若单一平台封禁严重，暂时切换至其他平台任务，等待封禁自动解除。

**预防建议**
- 使用付费的高质量代理服务，避免免费公开代理。
- 设置合理的请求间隔和并发上限，模拟真实用户行为。
- 监控 HTTP 状态码分布，在 403 比例升高时自动降低频率或切换代理。

### Q: LLM 分析失败/超时？

**现象描述**
- 任务在 LLM 分析阶段卡住，最终提示"请求超时"或"API 返回错误"。
- 分析结果为空或不完整。

**根因分析**
- LLM API 服务繁忙或网络延迟高，导致响应时间超过配置的超时时间。
- API Key 无效、额度用尽或模型名称填写错误。
- 输入的上下文（如评论文本）过长，超出了模型的最大 Token 限制。
- 本地部署的 LLM 服务未启动或端口配置错误。

**分步解决方案**
1. 检查 API Key 和 Base URL 配置是否正确，在终端中手动测试连通性：
   ```bash
   curl $BASE_URL/v1/models -H "Authorization: Bearer $API_KEY"
   ```
2. 增加超时时间：
   ```yaml
   llm:
     timeout_s: 120
   ```
3. 若上下文过长，启用文本截断或分段摘要策略：
   ```yaml
   llm:
     max_context_length: 8000
     strategy: chunk_summary
   ```
4. 切换到响应更快的模型（如从 GPT-4 切换到 GPT-3.5-Turbo）进行测试。
5. 若使用本地模型，确认服务进程已启动且端口、显存充足。

**预防建议**
- 对 LLM 调用添加指数退避重试机制。
- 在任务前预估文本长度，超长内容提前截断或分段。
- 准备备用模型配置，在主模型不可用时自动切换。

### Q: 输出文件在哪里？

**现象描述**
- 任务显示"已完成"，但找不到生成的 Excel、报告或下载的视频文件。
- 不确定默认输出路径是什么。

**根因分析**
- 输出路径未显式配置，使用了默认的相对路径，用户不清楚具体位置。
- Desktop 应用与命令行模式的默认输出目录不同。
- 文件被保存到了容器/虚拟环境的内部路径，而非宿主机的预期目录。

**分步解决方案**
1. 命令行模式下，默认输出目录为项目根目录的 `data/` 和 `output/` 文件夹：
   - Excel 数据：`output/平台名称_关键词_时间戳.xlsx`
   - 下载视频：`data/videos/`
   - 运行报告：`data/reports/`
2. Desktop 应用模式下，输出文件位于用户数据目录的 `results/runs/<runId>/` 下。
3. 在任务配置中显式指定 `output_dir`，避免使用容易混淆的默认路径：
   ```yaml
   output_dir: "/absolute/path/to/output"
   ```
4. 若使用 Docker 运行，确保正确挂载了宿主机目录：
   ```bash
   -v $(pwd)/output:/app/output
   ```
5. 在 Desktop 应用中，打开任务详情页的"产物"标签，可直接查看和导出文件。

**预防建议**
- 始终在配置文件中显式声明 `output_dir`，避免依赖易变的默认路径。
- 使用绝对路径而非相对路径，减少工作目录切换带来的困惑。
- 在团队协作时统一输出目录规范，并配置自动上传到共享存储。
